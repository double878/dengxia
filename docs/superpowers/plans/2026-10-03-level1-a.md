## 1. 数据契约（先定字段，再编码）

以下结构与字段名是 A 对 B（显示）和 C（录制）的对外契约。B/C 的模块尚不存在，A 用模拟接收端验证。字段名一旦进入本计划即视为契约，后续改动必须先报告影响。

### 1.1 通用约定

- **时间单位**：整数毫秒（`time_ms`）。歌曲时间 `0` = 本关音乐起点。
- **位置单位**：归一化，`0.0`–`1.0`。`stage_pos` 指影人**接地点（脚底）**在幕布坐标中的位置；`x` 向右为正，`y=0` 为舞台最深处、`y=1` 为最靠幕布/玩家处。
- **角度单位**：弧度（rad）。手臂角 `0` = 技术中性位，正值为抬起方向。
- **数值类型**：`float` 一律为 `float`，`time_ms`/`*_id`/`hook_slot` 一律为 `int`。契约中不使用 `bool` 表示三态。

### 1.2 `PuppetState`（A 产出 → B 显示 / C 录制）

| 字段 | 类型 | 单位/范围 | 含义 |
| --- | --- | --- | --- |
| `puppet_id` | `int` | `0`–`2` | 影人编号，全游戏三个 |
| `stage_pos` | `Vector2` | 各分量 `0.0`–`1.0` | 接地点在幕布中的归一化位置 |
| `stance` | `float` | `0.0`–`1.0` | `0.0` 完全站立，`1.0` 完全蹲下 |
| `facing` | `float` | `-1.0`–`1.0` | 连续转身量；`-1.0` 面向左，`0.0` 面向正面，`+1.0` 面向右 |
| `turn_progress` | `float` | `0.0`–`1.0` | `abs(facing)`，本帧转身过渡的完成程度 |
| `hand_angle` | `Vector2` | 各分量 `-0.6`–`+0.6` | `x` = 左手关节角，`y` = 右手关节角（弧度） |
| `head_id` | `int` | `-1`、`0`–`5` | `-1` = 未分配；全部影人与头架槽位共享这六个头 |
| `hook_slot` | `int` | `-1`、`0`、`1` | `-1` = 未挂起，否则为挂钩槽位 |
| `is_controlled` | `bool` | — | 是否当前直接受控 |

**不变量（每次 `tick()` 结束后都成立，测试逐条断言）：**

1. 全场恰好一个或零个影人 `is_controlled == true`。
2. 六个头各归属一个位置：所有影人 `head_id` 与头架槽位合起来，`0`–`5` 各出现恰好一次。
3. 同一 `hook_slot` 最多一个影人（`-1` 不占槽位）。
4. 同一挂钩位置不重复；`hook_slot = -1` 的影人可自由运动。
5. 连续量永不出界：`stage_pos` 各分量 ∈ [0,1]、`stance` ∈ [0,1]、`facing` ∈ [-1,1]、`abs(turn_progress)` ≤ 1、`abs(hand_angle)` 各分量 ≤ 0.6。
6. 到限后继续按住不产生额外动作（不入界外、不抖动）。

### 1.3 `TimedEvent`（A 产出 → C 录制 / B 表现）

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `time_ms` | `int` | 事件发生时的歌曲时间；切片 1 由 `TestClock` 提供，切片 2 起由 `MusicClock` 提供 |
| `kind` | `String` | 事件类型，见下表 |
| `object_id` | `int` | 影人编号（`0`–`2`） |
| `cue_id` | `String` | 对应 `Cue` 的唯一 ID；非判定事件为 `""` |
| `payload` | `Dictionary` | 事件载荷，至少含 `"kind"` 便于 JSON 化后辨识 |

| `kind` | 触发时机 | `payload` |
| --- | --- | --- |
| `pose_stance` | `stance` 由拖动改变，且在**开始变化**与**停止变化**时各发一次（不在每帧发） | `{"stance": float}` |
| `facing_turn` | 转身方向发生改变时（左 / 停 / 右，每次切换一次） | `{"from": float, "to": float}` |
| `hand_motion` | 某只手的**运动方向**发生改变时（抬 / 停 / 落） | `{"hand": "left"｜"right", "dir": -1｜0｜1, "angle": float}` |
| `drag_begin` / `drag_end` | 胸签拖动开始 / 结束 | `{"dragging": bool}` |

`hand_motion` 的 `dir`：`+1` 抬、`-1` 落、`0` 停（包含「冲突导致保持姿势」）。

**切片 1 不产生**：`cue_hit`、`cue_miss`、`remedy_*`、`applause`。这些属于切片 3、4，届时按本表扩展并在此文档登记。

### 1.4 A 对外提供的调用方式

```gdscript
# 构造。clock 是鸭子类型的时钟，切片 1 用 FrameClock，切片 2 起用 MusicClock。
var controller := PuppetController.new()
controller.clock = clock            # 需提供 get_song_time_ms() -> int
controller.setup(3)                 # 建立 0..2 三个影人，0 号受控

# 每帧一次。内部顺序：先改 PuppetState 并 clamp，再把事件写入队列。
# B 的显示与 C 的录制在同一帧读 state，因此一定读到改动后的值。
controller.tick(delta: float) -> void

# 输入（A 自己的测试入口直接调用；正式入口由 StageDirector 在切片 3 接）
controller.begin_drag(puppet_id: int, mouse_pos: Vector2) -> bool
controller.drag_to(mouse_pos: Vector2) -> void          # 累积位移，在 tick() 中应用
controller.end_drag() -> void
controller.apply_input(input_map: Dictionary) -> void    # 见下

# 状态读取（B/C 只读）
controller.puppets: Array[PuppetState]
controller.get_puppet(puppet_id: int) -> PuppetState

# 事件读取（取走即清空；C 的 Recorder 每帧调一次）
controller.take_events() -> Array[Dictionary]
```

`input_map` 的键（A 的 `InputReader` 产出与 `PuppetController` 消费的接口）：

```gdscript
{
    "left_raise":  bool,   # 按住 A
    "left_lower":  bool,   # 按住 Shift+A
    "right_raise": bool,   # 按住 D
    "right_lower": bool,   # 按住 Shift+D
    "both_raise":  bool,   # 按住 W
    "both_lower":  bool,   # 按住 S
}
```

单手的净方向 = `raise - lower`；`W`/`S` 对角色的净方向 = `both_raise - both_lower`，再叠加到每一只手。某只手的净方向为 `0`（含 `A`+`Shift+A` 同按、`W`+`S` 同按、`A`+`S` 净零）时，该手**保持当前姿势不变**。

### 1.5 时钟鸭子类型（切片 2 的接缝）

切片 1 只依赖一个方法：`get_song_time_ms() -> int`。切片 2 用 `MusicClock` 直接替换实现，`PuppetController`、测试场景、测试用例都不改。切片 1 的 `FrameClock` 与 `TestClock` 都放在 A 的测试目录内，不进入正式目录。

### 2.3 输入与行为细则

- `begin_drag`：鼠标左键按下时，若命中当前受控影人的胸签范围（占位图形用一个圆形热区，半径 90 px，随影人位置移动），开始拖动；否则忽略并返回 `false`。拖动中鼠标移动只累积位移，在 `tick()` 中应用，保证「拖动时维持双手已有姿势」。
- 横向位移 → `stage_pos.x`，到 `0.0`/`1.0` 截断。
- 纵向位移 → **向下拖 = 蹲下**（与画面直觉一致），`stance` 到 `0.0`/`1.0` 截断。
- `stage_pos.y` 切片 1 不参与操控（留给后续关卡的纵深调度），保留字段并 clamp。
- 转身：横向位移绝对值超过 `2 px` 时以符号设定目标方向 → `facing` 以 `4.0/s` 向 `±1.0` 平滑推进；横向静止时保持当前 `facing`。
- 双手：`A`/`D` 抬左手/右手，`Shift+A`/`Shift+D` 落左手/右手，`W`/`S` 双手同抬/同落。按住连续变化，松开保持；同手相反指令保持原姿势；角度到限后再按住不产生额外动作。
- 影人 0 初始受控；切片 1 不实现挂起/接手（属第 2 关范围），但 `head_id`/`hook_slot` 字段与不变量已就位并参与断言。

### 2.4 可观察的验收现象

在 Windows 图形环境运行 `scenes/a_test/a_controls_test.tscn`，应能同时看到：

1. 按住左键拖动占位影人的胸签圆圈，影人**连续**横向移动，松开后**停在新位置**。
2. 向下拖影人**蹲下**、向上拖**站起**；到顶/到底后继续拖不再变化，HUD 的 `stance` 停在 `1.000`/`0.000`。
3. 影人朝移动方向**渐进**翻面：HUD 的 `facing` 在约 0.25 s 内从 `-1.000` 走到 `+1.000`，中间能看到 `turn_progress` 在 `0`–`1` 之间连续取值，不是瞬间跳到 `±1`。
4. 按住 `A` 左手连续抬起、松开保持；`D` 只动右手；`Shift+A`/`Shift+D` 分别落下；`W`/`S` 双手同动。
5. 按住 `A` + `Shift+A` 时左手角度**冻结不变**，HUD 事件栏出现 `hand_motion dir=0`。
6. 所有连续量在 HUD 上永不超过 `[0,1]`、`[-1,1]`、`±0.600`。
7. 事件栏实时显示 `pose_stance`、`facing_turn`、`hand_motion`、`drag_begin`/`drag_end`，每条带 `time_ms`、`object_id`、`cue_id`、`payload`——这就是 B/C 将读到的同构数据。

**判定语义（重要，写下来避免误读）：**

- 判定的是「姿势到位或状态切换」的**瞬间**，不是连续移动的每一帧。
- `cue_fire` = 玩家做出了这个动作（物理动作确实发生了，供 B 表现）；`cue_hit`/`cue_miss` 才是合拍结果。三者分开，保证**错拍也照常发生**。
- 「到位」（`reach`）是连续状态，判定条件为**本次拖动中先离开过目标范围、再进入**：只要求「当前在范围内」会让玩家原地起拖就被判到位，那不是移动到到位。
- 去重键 = `cue_id` + 拖动代次：一次拖动里同一 Cue 只判定一次；新手势可再次判定，因此「错拍做一次、随后在窗内再做一次」都能被如实记录。

**实现中发现并修掉的坑：**

1. `Cue.gd` 与 `CueHint.gd` 互相 `preload` 引用常量会在**类解析阶段形成循环**，导致构造期 `Invalid call. Nonexistent function 'new' in base 'GDScript'`。已让 `CueHint` 只用自己的同名字符串常量。
2. `_evaluate_reach` 曾先写去重键再交给 `_register_action`，后者读到同一个键就跳过，**导致「到位」永远不会被判定**。已把去重统一收敛到 `_register_action`。
3. `pose_stance` 曾在同一帧重复发两条事件（`_apply_drag` 一条、`_settle_stance` 一条）。已在 `_apply_drag` 里同时更新 `_stance_last_emitted`。
4. 「站起」的目标范围一开始误写成 `[0.7, 1.0]`（那是**蹲下**方向），会让蹲到底被判成站起。已改为 `[0.0, 0.05]`，并在数据测试里断言「站起与蹲下的范围方向必须相反」。
5. 测试台 `begin_drag()` 曾额外步进一帧，使「按下」与「移动」分处两次 tick，累计位移被清零，姿势推不到位。已改为不步进。

`cue_miss` 的 `payload` 增加 `"reason": "missed_outright"` 以区分「完全没做」与「错拍做了」。

**实现中发现并修掉的坑（写下来避免重犯）：**

1. **补救永远不可能成功。** `_can_attempt` 原先要求「上次判定的时间戳早于判定窗左端、且当前又回到窗内」，而 `detect_misses` 写入漏做结果用的时间戳在窗**右端之后**，于是该条件永不成立：玩家在窗口内补做动作时，判定被静默丢弃（实测补做后 `outcome.time_ms` 仍停在落点时刻）。改为「命中即定案、未命中仍可再判」，去重交给 `_register_action` 的「一次拖动同一 Cue 只判一次」。
2. **低合拍补救被漏做补救挤掉。** `_first_open_cue_in_segment` 只跳过「已判定」的 cue，而漏做路径会为段内每条漏做的 cue 开窗，段内第一条漏做的 cue 因此几乎总是已有窗口；调用方再 `continue` 一次，使「跌破警戒线触发补救」在本关数据下**永远不生效**。改为同时跳过已开窗的 cue，并删掉调用方那句冗余的 `continue`。
3. **测试 02/10 把示范规则写成了实现细节的巧合。** 2760 ms 时蹲下与站起两条漏做都开了窗（截止 9510 / 10760），同屏只能示范最早到期的一条，而实现选的正是蹲下；测试却按「2760 ms 只有一个窗口」写断言，10 号测试则依赖字典迭代顺序才恰好通过。已把断言改为按「最早到期」规则计算。
4. **`mark_hit` 是无人调用的死代码**，已删除；`was_attempted` 也不再被生产代码引用，一并删除。
5. **补救成功不能把 `hit` 翻正。** `hit` 一旦为 `false` 就保持 `false`，补救只补「把动作做出来」，原失误永远留在结果与记录里（`remedy_attempt` 标记这是补做）。
6. **畸形事件会打断整帧判定，而且只进日志。** 事件入口直接对元素调 `e.get()`，`null` 或字符串元素会抛 `Invalid call. Nonexistent function 'get' in base 'Nil'/'String'`；Godot 只把它写进日志并继续执行，所以**看起来「没崩」，其实该帧的判定已经中断**。入口补 `is Dictionary` 判断。

   > 这一条是被前置验收抓出来的：我自己先写的排查脚本只打印「未崩溃」，把日志里的 `SCRIPT ERROR` 当成了通过，结论一度是错的。教训是**「没崩溃」不等于「没报错」**，判断健壮性必须同时看 stderr。
7. **缺 payload 的 `pose_stance` 能伪造一次动作，甚至关掉正在开的补救窗口。** `payload.get("stance", 0.0)` 在字段缺失时按 `0.0` 处理，而 `stance = 0.0` 正是「站起」的到位范围，于是一个空 payload 事件被如实判成一次真实站起，并把 `l1_c1_stand` 的补救窗口当作「补做成功」关掉。已改为**没有 `stance` 读数就不判定**——宁可不判定，也不接受没有读数的动作事件。

**关于低合拍路径的实测结论（如实记录，不夸大）：**

在**标准第一关数据**下，低合拍路径不会开窗——因为 5000 ms 之后每条落点都先被漏做路径接管并开窗，「移步」段已无「既未判定、又未开窗」的落点可选。测试 11 因此**额外追加一条落点**（`l1_c_slide`，第 18 拍）把这条路径单独隔离出来，证明机制可用、理由为 `low_sync`、可补做成功且原失误保留。低合拍阈值与「何时才算跌到警戒线」仍需游玩实测校准。

## 9. 导出包「一打开就卡住」的排查记录（2026-10-03 第二轮）

**顺带修掉的真实缺陷：**
